# CT-OS V4.0 面板功能梳理与重设计计划

> Created: 2026-04-28
> Scope: Web 桌面端信息架构、主面板职责、重复功能收敛
> Status: Phase A implemented, deeper panel work pending
> 交易相关内容仅供参考，不构成投资建议。

## 目标

把 CT-OS 从“多个功能页都在讲一点交易建议”收敛成“每个面板只负责一个用户任务”。

当前问题不是功能不够，而是几个面板在重复回答同一组问题：

- 今天该看哪些票？
- 为什么值得看？
- 风险线在哪里？
- 下一步动作是什么？
- 这个动作和我的持仓有什么关系？

这些问题现在散落在 `今日作战`、`今日机会`、`缠论看盘/Radar`、`调仓罗盘`、`交易看板` 里。用户会来回跳页，系统也会重复生成类似的计划、风险和结构解释。

重设计目标：

1. 每个面板有唯一职责。
2. 所有“下一步动作”统一进入作战队列。
3. 所有“单票深度结构”统一进入雷达工作台。
4. 所有“候选发现”统一进入机会池。
5. 所有“持仓和交易事实”统一进入交易账本。
6. 行为复盘和训练从主交易流里分离，避免盘中干扰。

## 当前面板盘点

| 当前导航 | 文件 | 当前职责 | 问题 |
|---|---|---|---|
| 交易看板 | `web/src/pages/Dashboard.jsx` | 持仓概览、健康度、T+1、风险预警、交易录入、最近交易 | 名字像总控台，但实际更像账户/交易账本 |
| 行为分析 | `web/src/pages/BehaviorReport.jsx` | 纪律评分、行为诊断、交易习惯 | 职责清楚，可以保留，但应接入作战反馈闭环 |
| 今日作战 | `web/src/pages/DailyPlaybook.jsx` | 从持仓、Scanner、自选股生成观察项和响应 | 应成为行动队列的唯一入口，但目前仍像独立计划页 |
| 今日机会 | `web/src/pages/Scanner.jsx` | 扫描结果、LLM 调研、质量过滤、加入观察 | 和今日作战重复“值得关注”的表达 |
| 缠论看盘 | `web/src/pages/ChanView.jsx` | 自选股、搜索、K线、图层、Radar 单票深度 | 职责清楚，是单票工作台 |
| 调仓罗盘 | `web/src/pages/RotationCompass.jsx` | 持仓与候选比较、预案、强弱排序 | 和今日作战、Radar 都重复“预案/动作” |
| 模拟训练 | `web/src/pages/SandTable.jsx` | 历史回放、买卖训练、评分 | 职责清楚，但更像复盘训练，不该占盘中主导航优先级 |

## 重复点

### 重复 1：动作计划分散

`DailyPlaybook` 有作战项、触发条件、失效条件、止损参考、响应按钮。
`RadarPanel` 有持仓联动、执行确认、触发剧本、场景 A/B/C。
`RotationCompass` 有持仓动作、触发条件、雷达复核、候选比较。
`Scanner` 详情里也展示止损、目标、赔率和调研结论。

结论：只有一个地方能代表“今天我下一步该响应什么”。这个地方应该是新版 `作战台`。

### 重复 2：候选和观察混在一起

Scanner 的候选可以“入观察”。Watchlist 也在 ChanView 里。DailyPlaybook 又从 `positions/scanner/watchlist` 生成计划。RotationCompass 再把 holdings 和 candidates 拉到一起比较。

结论：候选生命周期要明确：

```text
扫描候选 -> 机会池复核 -> 加入观察 -> 进入作战队列 -> 雷达深看 -> 用户响应 -> 行为复盘
```

Scanner 只负责“扫描候选和质量过滤”，不负责最终作战排序。

### 重复 3：持仓风险被多个页面表达

Dashboard 有 warnings 和健康度。Radar 有最近风险线和持仓联动。RotationCompass 有防线和距离。DailyPlaybook 有止损参考。

结论：持仓事实归 `交易账本`，持仓当日风险响应归 `作战台`，单票结构解释归 `雷达工作台`。

### 重复 4：AI 调研和确定性规则边界容易混

Scanner 文案已经写了“LLM 只做调研排雷”，这是对的。后续所有面板都要保持这个边界：

- 确定性结构、触发、风险线来自 Strategy/Radar/Chan。
- AI 只能解释、总结、提示红旗，不能成为规则事实。

## 新版面板分工

推荐把顶部主导航从 7 个收敛为 5 个：

```text
作战台 | 雷达工作台 | 机会池 | 交易账本 | 复盘训练
```

### 1. 作战台

替代当前 `今日作战`，成为默认首页。

唯一职责：今天要处理的事件队列。

包含：

- 持仓风险：止损接近、T+1 锁定、结构失效、逆势风险。
- 机会触发：观察股达到策略触发条件。
- 日内T窗口：冲高减T、回落接回、接近变盘、小级别确认。
- 候选待复核：Scanner 高质量候选需要用户决定是否纳入观察。
- 计划响应：忽略、观察、已处理、去雷达复核。
- 数据健康：过期数据只能复核，不能触发行动。

不包含：

- 不展示完整候选列表。
- 不展示完整 K 线。
- 不做交易录入。
- 不输出新的结构结论，只引用 Radar/Strategy 结果。

数据来源：

- `/api/playbook/today`
- 未来 `coach_events`
- `positions`
- `scan_results`
- `watchlist`
- `radar freshness`

### 2. 雷达工作台

保留并强化当前 `缠论看盘`。

唯一职责：单只股票的深度判断和结构复核。

包含：

- 自选股/搜索。
- K 线图。
- 图层控制。
- Radar 结构、场景、边界、触发剧本。
- 当前 symbol 的作战项上下文。
- 当前 symbol 的数据源和 freshness。

不包含：

- 不做全市场候选扫描。
- 不做持仓列表总览。
- 不做跨股票排序。

调整：

- `RadarPanel` 继续在右侧。
- `WatchlistPanel` 可以保留左侧。
- 从作战台、机会池、交易账本跳入时，带入 `source_context`，例如 “来自作战项/来自候选/来自持仓风险”。

### 3. 机会池

由当前 `今日机会` 改名。

唯一职责：发现、过滤、整理候选。

包含：

- Scanner 状态。
- 候选列表。
- 质量过滤。
- 技术入选原因。
- AI 调研红旗。
- 加入观察。
- 删除候选。

不包含：

- 不做最终行动排序。
- 不和持仓横向比较。
- 不展示完整作战计划。

调整：

- “入观察”后不应该直接消失到黑洞，要明确进入哪个观察组，以及是否会被下次作战台读取。
- 详情抽屉只保留候选证据，不写“仓位动作”。

### 4. 交易账本

由当前 `交易看板` 改名。

唯一职责：用户事实和账户事实。

包含：

- 持仓列表。
- 成本、数量、盈亏、T+1。
- 交易录入。
- 最近交易编辑/删除。
- 持仓健康度。
- 交易导入。

不包含：

- 不展示候选机会。
- 不做结构推演。
- 不做调仓建议排序。

调整：

- `PositionList` 的“看盘”跳转到雷达工作台。
- warnings 保留，但只写事实类风险，例如集中度、T+1、止损未设置。策略触发类事件进入作战台。

### 5. 复盘训练

合并当前 `行为分析` 和 `模拟训练` 的主导航空间。

唯一职责：盘后复盘、纪律训练、交易能力提升。

包含两个内部 tab：

- 行为体检：纪律评分、胜率、盈亏比、止损执行、计划外交易。
- 模拟训练：历史回放、沙盘买卖、训练评分。

不包含：

- 不推送盘中 action。
- 不展示今日候选池。
- 不替代交易账本。

调整：

- Behavior Report 增加来自作战台的响应数据：计划内/计划外、忽略触发、执行后结果。
- SandTable 的训练结果未来写入训练记录，不污染真实交易。

## 调仓罗盘怎么处理

`调仓罗盘` 不建议继续作为顶级导航。

它的价值是真实的：持仓和候选横向比较。但它不是独立用户旅程，而是两个场景里的工具：

1. 作战台里，当用户要决定“处理持仓还是看候选”时，需要一个比较抽屉。
2. 交易账本里，当用户审视持仓结构时，需要一个“持仓 vs 观察”的比较模块。

建议：

- 从顶级导航移除。
- 保留 API `/api/rotation/compass`。
- UI 降级为 `RotationDrawer` 或 `ComparisonPanel`。
- 入口放在作战台和交易账本。

这样不会丢功能，只是把它放到真实决策发生的地方。

## 用户流

### 盘前

```text
打开作战台
  -> 生成今日作战队列
  -> 查看持仓风险和观察触发
  -> 对重点票进入雷达工作台复核
  -> 标记“今日只看这些”
```

### 盘中

```text
作战台接收触发/风险事件
  -> 用户点开单条事件
  -> 去雷达工作台确认结构
  -> 用户在券商 App/QMT 手动处理
  -> 回到作战台记录响应
```

### 盘后

```text
交易账本补录真实交易
  -> 作战台对照计划响应
  -> 复盘训练生成行为诊断
  -> 机会池更新候选状态
```

## 导航命名建议

| 当前 | 建议 | 理由 |
|---|---|---|
| 交易看板 | 交易账本 | 当前主要是账户和交易事实，不是总控台 |
| 行为分析 | 复盘训练 / 行为体检 | 和模拟训练合并后更完整 |
| 今日作战 | 作战台 | 成为默认首页和事件队列 |
| 今日机会 | 机会池 | 不暗示今天必须行动 |
| 缠论看盘 | 雷达工作台 | 更贴近单票深度复核 |
| 调仓罗盘 | 降级为比较抽屉 | 避免顶层重复 |
| 模拟训练 | 并入复盘训练 | 训练不是盘中主任务 |

## 后端职责收敛

未来后端也要减少重复输出：

| 域 | 主 API | 职责 |
|---|---|---|
| 作战队列 | `/api/playbook/today` | 汇总今天该响应的事件 |
| 单票雷达 | `/api/radar/{symbol}` | 单票结构、场景、边界、计划 |
| 候选发现 | `/api/scan/results` | 候选发现和质量过滤 |
| 交易事实 | `/api/positions/*`, `/api/trades/*` | 用户事实 |
| 比较工具 | `/api/rotation/compass` | 被作战台/账本调用，不是顶级产品 |
| 复盘训练 | `/api/behavior/*`, `/api/sand-table/*` | 盘后分析和训练 |

关键原则：

- `Radar` 是单票事实和结构解释。
- `Playbook` 是多来源 action queue。
- `Scanner` 是候选发现。
- `Rotation` 是比较工具。
- `Behavior` 是事后评价。

## UI 布局方向

必须遵守 `DESIGN.md` 的工业/军用功能主义风格。

建议桌面布局：

```text
┌─────────────────────────────────────────────────────────────┐
│ 顶部状态栏：CT-OS / 市场状态 / 数据源健康 / 设置             │
├─────────────────────────────────────────────────────────────┤
│ 主导航：作战台 | 雷达工作台 | 机会池 | 交易账本 | 复盘训练    │
├───────────────┬───────────────────────────┬─────────────────┤
│ 左侧列表/池子 │ 主工作区                   │ 右侧详情/指令面板│
│ 事件/自选/候选│ 图表/表格/复盘             │ 雷达/详情/响应    │
└───────────────┴───────────────────────────┴─────────────────┘
```

不要做营销式首页。默认打开作战台。

## 实施顺序

### Phase A：产品收敛，不改数据模型

Implementation status: completed on 2026-04-28.

1. 改导航命名和顺序。
2. 将默认页改为 `playbook`。
3. 将 `RotationCompass` 从顶级导航移除，保留入口。
4. 将 `BehaviorReport` 和 `SandTable` 合并进 `ReviewTrainingPage`。
5. 将 `Scanner` 文案改为 `机会池`，限制“动作建议”表达。

验收：

- 顶部导航最多 5 项。
- 用户能从作战台进入雷达复核。
- 用户能从机会池加入观察。
- 用户能从交易账本录入交易。
- 调仓比较仍可访问，但不占顶级导航。

### Phase B：作战队列成为唯一行动入口

Implementation status: UI queue framing and source tracking implemented on 2026-04-28.

1. `DailyPlaybook` 改为 `CommandDeck`。
2. 作战项统一显示来源：持仓、观察、候选、数据风险。Done for `positions/scanner/watchlist`.
3. 引入状态：`WATCHING`, `TRIGGERED`, `BLOCKED`, `RESPONDED`, `INVALIDATED`。Frontend now groups existing statuses into `需处理/观察中/数据复核/已响应`; backend status normalization remains pending.
4. 引入结构化队列分组：`临界变盘`, `T窗口`, `小级别确认`, `持仓防线`, `观察池`, `复核/失效`。
5. 日内T事件遵守 `docs/INTRADAY_T_PLAN_CONTRACT.md`：雷达/策略产出，作战台消费，不在作战台重做算法。
6. 作战项响应写入后续 Behavior Report。
7. stale 数据只允许“去雷达复核”，不允许 action 触发。

验收：

- 任何“下一步响应”只在作战台出现。
- Radar 和 Scanner 只提供证据，不抢作战台的决策位。
- 日内T只显示 `接近/确认/失效/已响应`，不显示自动买卖语言。

### Phase C：比较工具组件化

1. 从 `RotationCompass.jsx` 提取 `ComparisonPanel`。
2. 作战台详情中可以打开比较抽屉。
3. 交易账本可以打开持仓 vs 观察比较。

验收：

- `/api/rotation/compass` 保留。
- 顶级导航不再有调仓罗盘。
- 比较信息出现在真实决策上下文里。

### Phase D：复盘训练闭环

1. 新建 `ReviewTrainingPage`。
2. 内部 tabs：行为体检、模拟训练。
3. Behavior Report 接入 playbook response metrics。
4. SandTable 训练结果独立记录，不混入真实交易。

验收：

- 盘中主导航不被训练页打断。
- 盘后可以看到“计划 -> 响应 -> 真实交易 -> 结果”的闭环。

## 风险与注意

- 不要为了合并导航把代码强行大重构。先做页面编排和命名，后做数据闭环。
- 不要删除 `/api/rotation/compass`，它只是从产品顶层降级为工具。
- 不要让 Scanner 输出交易动作，它只输出候选证据。
- 不要让 Behavior Report 再承担持仓风险解释，它只做事后复盘。
- 不要把 QMT、TDX preview 数据带进正式 Radar 结构判断。

## 当前推荐决策

推荐先做 Phase A。

理由：这是最小但最有效的一刀。用户会立刻感到产品从“七个页面到处找东西”变成“先看作战台，再去雷达复核，盘后复盘”。不需要改数据库，也不碰 QMT/TDX/策略底层，风险低。
