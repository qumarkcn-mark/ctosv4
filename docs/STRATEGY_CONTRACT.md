# CT-OS V4.0 Strategy Contract

> Created: 2026-04-24
> Depends on: `docs/ARCHITECTURE_FOUNDATION_DECISIONS.md`, `docs/DATA_SOURCE_CONTRACT.md`

This contract defines how CT-OS represents trading-coach strategies.

Strategies turn structure facts and user context into plans, alerts, and optional Phase 3 execution intent candidates.

Strategies do not directly call UI, push services, LLM, or QMT.

## Core Boundary

Strategies may output:

- plans
- watch conditions
- alerts
- risk notes
- coach event payloads
- Phase 3 execution intent candidates

Strategies must not:

- place orders
- call QMT
- send push notifications directly
- write UI-only prose as their only output
- bypass data freshness checks
- let AI determine deterministic rule outcomes

Phase 1/2 strategies are coach-only. They produce plans and alerts with "仅供参考".

Phase 3 strategies may produce execution intent candidates, but only Execution Layer can consume them.

## Strategy Definition

A strategy definition describes a reusable rule set.

Recommended shape:

```json
{
  "strategy_id": "war1_third_buy",
  "strategy_version": "1.0.0",
  "name": "战法一：日线三买",
  "scope": ["scanner", "radar", "alerts"],
  "mode": ["EMPTY"],
  "description": "日线中枢突破后回踩不破，等待次级别确认。",
  "inputs": {
    "structure": ["day", "30", "5"],
    "position": false,
    "market_context": true,
    "user_config": true
  },
  "freshness_required": true,
  "outputs": ["plans", "alerts"],
  "disclaimer_required": true
}
```

Required fields:

| Field | Meaning |
|---|---|
| `strategy_id` | stable machine ID |
| `strategy_version` | semantic version of rule behavior |
| `name` | human-readable name |
| `scope` | where the strategy can run |
| `mode` | `EMPTY`, `HOLDING`, `ROTATION`, `SCANNER`, `EXECUTION_CANDIDATE` |
| `inputs` | required inputs |
| `freshness_required` | whether stale data blocks output |
| `outputs` | allowed output types |

## Strategy Input Contract

Strategies consume normalized structured inputs.

```json
{
  "symbol": "sh.600519",
  "user_id": 1,
  "as_of": "2026-04-24T20:35:00+08:00",
  "mode": "EMPTY",
  "data_source": {
    "structure": "baostock",
    "adjustflag": "2"
  },
  "freshness": {
    "is_stale": false,
    "stale_reason": ""
  },
  "structure": {
    "levels": []
  },
  "position": null,
  "user_config": {},
  "market_context": {}
}
```

Rules:

- `symbol` must be canonical internal format.
- Formal structure must come from `chan.py adapter`.
- Strategies must check freshness before producing trading-action alerts.
- Holding strategies must receive user position context.
- Empty-position strategies must not pretend the user has a holding.

## Condition Contract

Conditions are deterministic rule checks.

```json
{
  "condition_id": "day_breakout_above_zg",
  "label": "日线突破中枢上沿",
  "status": "PASS",
  "severity": "INFO",
  "evidence": {
    "level": "day",
    "zg": 12.34,
    "close": 12.58
  }
}
```

Allowed `status` values:

| Status | Meaning |
|---|---|
| `PASS` | condition is satisfied |
| `FAIL` | condition is not satisfied |
| `WATCH` | close but not confirmed |
| `BLOCKED` | cannot evaluate due to missing/stale data |

Allowed `severity` values:

| Severity | Meaning |
|---|---|
| `INFO` | explanatory |
| `WATCH` | user should observe |
| `WARNING` | risk is rising |
| `CRITICAL` | deterministic risk condition triggered |

Conditions must store evidence as structured data, not only prose.

## Plan Contract

Plans describe what the coach is watching.

```json
{
  "plan_id": "war1_wait_5m_confirm",
  "plan_type": "ENTRY",
  "title": "等待 5 分钟确认",
  "status": "WATCHING",
  "conditions": ["day_breakout_above_zg", "m30_structure_ready", "m5_buy_signal"],
  "action_label": "触发后检查是否入场",
  "risk": {
    "invalid_if": "跌回日线中枢上沿下方",
    "stop_reference": {
      "source": "structure",
      "level": "day",
      "field": "zd"
    }
  },
  "disclaimer": "仅供参考，不构成投资建议"
}
```

Allowed `plan_type` values:

| Type | Meaning |
|---|---|
| `ENTRY` | empty-position entry watch |
| `HOLDING` | holding management |
| `REDUCE` | reduce-position watch |
| `EXIT` | exit-risk watch |
| `ROTATION` | compare holding/candidate |
| `TRAINING` | sand-table training |
| `EXECUTION_CANDIDATE` | Phase 3 candidate intent, not executable by itself |

Allowed `status` values:

| Status | Meaning |
|---|---|
| `WATCHING` | not triggered yet |
| `TRIGGERED` | condition triggered |
| `BLOCKED` | data/risk blocks plan |
| `INVALIDATED` | plan invalidated |
| `COMPLETED` | plan done |

## Alert Contract

Alerts are delivery candidates generated by strategy rules.

```json
{
  "alert_id": "war1_m5_confirmed",
  "alert_type": "STRATEGY_TRIGGER",
  "priority": "HIGH",
  "trigger": {
    "condition_id": "m5_buy_signal",
    "triggered_at": "2026-04-24T10:35:00+08:00"
  },
  "message": {
    "title": "5 分钟确认信号出现",
    "body": "战法一观察条件触发，请检查日线中枢和 5 分钟买点。仅供参考。"
  },
  "dedupe_key": "1:sh.600519:war1_third_buy:m5_buy_signal:2026-04-24",
  "expires_at": "2026-04-24T15:00:00+08:00"
}
```

Allowed `priority` values:

| Priority | Meaning |
|---|---|
| `LOW` | background info |
| `NORMAL` | normal reminder |
| `HIGH` | important watch condition |
| `URGENT` | risk condition |

Rules:

- Alerts must be generated from deterministic conditions.
- Alerts must include a dedupe key.
- Trading-action alerts require fresh data.
- Message body must include "仅供参考" when it implies any trading action.
- Push delivery is handled by Push Service, not strategy code.

## Coach Event Payload

Every meaningful strategy trigger should be recordable as a coach event.

```json
{
  "event_type": "STRATEGY_TRIGGERED",
  "user_id": 1,
  "symbol": "sh.600519",
  "strategy_id": "war1_third_buy",
  "strategy_version": "1.0.0",
  "plan_id": "war1_wait_5m_confirm",
  "condition_id": "m5_buy_signal",
  "data_source": {
    "structure": "baostock",
    "adjustflag": "2"
  },
  "freshness": {
    "is_stale": false
  },
  "evidence": {}
}
```

Coach events support behavior review, alert audit, and future strategy refinement.

## Phase 1 Strategy Use

Phase 1 mostly uses strategy contract for Radar display.

Allowed:

- show empty-position plan
- show holding-management plan
- show why a condition is blocked
- show data source and freshness

Not allowed:

- send push
- generate execution intent
- call QMT

## Phase 2 Strategy Use

Phase 2 uses strategies for scanner, radar, rotation, and alerts.

Allowed:

- scanner candidate plans
- watchlist monitoring
- holding risk alerts
- rotation comparison
- coach events
- user-specific strategy configs

Not allowed:

- automatic order placement
- QMT integration for public users
- AI deciding strategy pass/fail

## Phase 3 Strategy Use

Phase 3 private strategies may produce execution intent candidates.

Example:

```json
{
  "plan_type": "EXECUTION_CANDIDATE",
  "strategy_id": "intraday_t_base_position",
  "intent_candidate": {
    "symbol": "sh.600519",
    "side": "SELL",
    "quantity_policy": "MAX_30_PERCENT_FLOATING",
    "price_source": "QMT_QUOTE_REQUIRED",
    "requires_risk_gate": true
  }
}
```

This is not an order.

Only Execution Layer may convert an approved candidate into an execution intent.

## User Configuration

User-specific strategy config should be separate from strategy definitions.

Example:

```json
{
  "user_id": 1,
  "strategy_id": "war1_third_buy",
  "enabled": true,
  "params": {
    "min_reward_ratio": 2.0,
    "max_atr_pct": 0.08,
    "alert_on_watch": true
  }
}
```

System templates are shared.

User configs are private.

## Versioning Rules

- Changing thresholds changes strategy version.
- Changing condition semantics changes strategy version.
- UI copy changes do not require strategy version changes.
- Every coach event and alert should store `strategy_id` and `strategy_version`.
- Backtests and behavior reports should reference the version used at trigger time.

## Required Tests

Initial strategy tests should cover:

- stale freshness blocks trading-action alerts
- strategy output contains deterministic evidence
- alerts include dedupe keys
- Phase 1/2 strategies do not produce executable orders
- Phase 3 execution candidates are not treated as orders
- AI output cannot alter condition status
- strategy version is preserved in coach event payload
